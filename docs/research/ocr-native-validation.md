# OCR 原生程序第二轮验证

日期：2026-11-16。状态：本机原生实验完成，尚未接入插件协议、宿主或发行流程。

后续已完成[插件任务与私有 worker 接入](../adr/0067-ocr-private-worker-lifecycle.md)，下文保留第二轮独立实验数据及当时的验证范围。

## 结论

原生路线可行：Go PNG 解码 + RapidOCRLite C ABI 已完成检测、几何裁切、识别与 CTC 解码，运行时不需要 Python、OpenCV 或 ONNX Runtime。沿用第一轮同一份 PP-OCRv6 small 权重和合成图片。

- 独立运行目录 **33.28 MiB**，ZIP **26.84 MiB**，均小于 64 MiB。目录已复制到新位置，模型、字典、原生库都从迁移后的目录读取。
- 严格浮点构建的 11 个样本各执行 5 次，文字全部稳定；密集图连续 100 次也稳定。普通样本比 ORT 原型慢，不能声称结果逐字等价。
- 全样本峰值 **347.0 MiB**，100 次密集图峰值 **348.9 MiB**。销毁引擎和强制回收 Go 内存后 RSS 未明显下降，不能用释放句柄实现可靠的空闲内存回收。
- 工作进程可被终止并回收，本轮强制取消后约 **4.3 ms** 完成 wait/reap。这是本机一次观测，不是性能承诺。
- **不能直接使用上游默认构建选项**：本机 `-ffast-math` 构建出现漏行及重复输出变化。追加 `-fno-fast-math` 后本轮问题不再复现，但尚未定位底层根因，也未验证其他编译器/平台。

建议保留 ORT 作为质量基线，以“按需运行的原生 OCR 工作进程”继续设计插件化；先解决父子进程生命周期，再接入 UI。RapidOCRLite 仍为 alpha 依赖，尚未决定作为正式发行默认引擎。

## 构建与边界

- Apple M4 Max、36 GiB RAM、macOS arm64；Go 1.26.0，Apple clang version 21.0.0 (clang-2100.1.1.101)，cmake version 4.4.5，Ninja 1.13.2.git.kitware.jobserver-pipe-1。
- 上游 tag `v5.0.0a6`，提交 `63bef543c782a0d81db2af056e1dfba550c6dd87`；从源码构建最终库，没有使用 Python wheel 中的库作为最终产物。
- CPU/NEON 4 线程、检测长边 960、识别 batch=1、方向分类关闭，关闭 Vulkan/Metal。CMake include 延迟追加严格浮点选项，实际命令末尾为 `-fno-fast-math`；上游源文件保持干净。
- Go 仅依赖标准库及 CGO C ABI，独立 go.mod 不进入宿主模块。原生构建和 go vet 通过，不改变应用依赖、协议、权限或内核业务。
- 完整目录还包含两份模型、字典和实验归属资料。otool 仅发现本地推理库与系统运行库，无 Python/ORT/OpenCV 动态依赖。
- **没有 manifest、stdio RPC、插件 SDK、业务 UI、正式签名及完整再分发归属审核**。这是独立识别运行目录的体积验证，不是完整插件安装或正式发行验收；剩余约 30.72 MiB 用于后续接入。

## 样本对照

使用与第一轮 SHA-256 相同的 11 张 PNG 和两份权重；字典从识别模型的 character 元数据导出。Go 自行解码 PNG 并将透明背景合成到白色。没有读取真实剪贴板、屏幕或用户文件，没有启动桌面、WebView、浏览器或授权窗口。

暖机重复 5 次取中位数，包含解码和前后处理。错误数忽略空白，保留大小写和标点，不衡量代码缩进、空格与换行恢复。两轮在同一机器不同时间执行，未严格控制其他负载，耗时比较仅作参考。

| 场景 | ORT 错误数 | 原生错误数 | ORT 耗时 ms | 原生耗时 ms |
| --- | ---: | ---: | ---: | ---: |
| 浅色中英混排 | 0 | 0 | 55.0 | 115.0 |
| 深色中英混排 | 0 | 0 | 54.8 | 120.7 |
| 12 px 小字 | 0 | 0 | 38.7 | 98.8 |
| 低对比度 | 0 | 0 | 55.2 | 121.0 |
| 倾斜 3° | 0 | 0 | 58.7 | 99.5 |
| 透明背景 | 0 | 0 | 58.3 | 114.6 |
| 终端 / 代码 | 0 | 1 | 56.9 | 102.8 |
| 24 行密集文字 | 1 | 0 | 329.2 | 467.8 |
| 双栏（先左后右） | 38 | 38 | 57.6 | 91.2 |
| 表格逐行文本 | 0 | 0 | 71.2 | 78.3 |
| 空白图 | 0 | 0 | 17.4 | 36.6 |

原生程序把 `go test ./...` 识别为 `go test /...`，丢失一个点；密集图没有出现 ORT 原型的逗号差异。因此两组输出与 ORT 不一致，不能宣称无损替换。双栏仍左右交错输出，需后续排序；表格只验证逐行文字。

初始化约 83.8 ms，首图约 117.9 ms，不含进程启动；文件缓存未清空或控制，不能当作整机冷启动指标。

## 默认浮点构建失败对照

默认 fast-math、4 线程时，`light` 和 `dense` 用例输出不稳定，出现整行丢失。浅色图 20 次复测仍不稳定；单线程下该图稳定但仍缺标题。关闭 fast-math 后，同图 20 次恢复完整四行并稳定，完整 11 图及 100 次密集图复测也稳定。

这支持将严格浮点作为本机后续构建条件，但不是根因证明或跨平台修复证明。默认构建失败、单线程诊断和严格构建的数据均保留在[证据数据](ocr-native-validation-results.json)。上游仍有未使用变量/函数等编译警告，本轮没有修改或修复上游算法。

## 内存、退出与取消

- 全样本后 RSS 为 347.0 MiB，销毁引擎并调用 Go FreeOSMemory 后为 347.0 MiB。
- 100 次密集图后 RSS 为 323.9 MiB，销毁与回收后为 324.2 MiB。文字一致不等于长期无泄漏，本轮未记录长期内存曲线。
- 正常任务、压力任务和取消任务均完成 wait/reap，PID 不再存在。正常与压力任务未观察到后代进程。取消是在运行中的长任务上终止整个工作进程组，不是协作式中断 C++ 内部运算。
- 畸形 PNG、超过 1600 万像素的 PNG 返回明确错误并退出，没有崩溃；输入另限 8 MiB，不开放网络图片输入或 shell 命令。
- 正式原生基准在 macOS 系统级禁网下运行，工作进程接收明确环境白名单。该实验机制不等于插件安全沙箱。

现有宿主[不保证回收插件任意后代进程](../plugin-protocol.md#核心恢复接口)。插件若另起 OCR worker，需要处理后台崩溃、禁用/卸载、宿主退出和孤儿进程。本轮外部脚本的取消成功不能代替该生命周期设计，也没有因此扩大宿主运行时能力。
