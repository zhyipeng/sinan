# OCR 引擎第一轮验证

日期：2026-11-16。状态：离线引擎验证完成，尚未开发或发布 OCR 插件。

后续已完成[第二轮原生程序验证](ocr-native-validation.md)：在本机验证了较小的独立识别运行目录、严格浮点构建和工作进程回收；下文保留第一轮 Python 实测数据及当时的验证边界。

## 结论

- PP-OCR + ONNX Runtime 能在本机离线完成中英文图片识别。建议以 **PP-OCRv6 small** 作为质量基线，v5 mobile 保留为包体积更宽裕的候选；tiny 在密集小字上错误较多，不建议直接作为默认模型。
- 三套模型都未正确处理双栏阅读顺序，需要额外版面排序。表格只验证逐行文字，不代表支持表格结构恢复。
- Python 原型依赖体积超过 64 MiB，内存偏高，不能直接作为插件发行。下一阶段验证原生处理链、运行库裁剪和任务后内存回收。
- 本轮未改变协议、权限或宿主运行时，不构成架构决策或平台支持声明。

## 条件与方法

- Apple M4 Max、36 GiB RAM、macOS arm64。Windows/Linux、其他架构未运行、未交叉构建。
- Python 3.12.12、RapidOCR 3.9.2、ONNX Runtime 1.32.0、NumPy 2.5.4；完整版本、模型及样本 SHA-256 见 [结果数据](ocr-validation-results.json)。依赖在独立临时环境中安装，和应用依赖分开；uv 脚本锁文件与实测环境逐项核对一致。
- 11 张人工生成 PNG，使用 Hiragino Sans GB 字体。没有读取真实剪贴板、屏幕或用户文件，没有启动桌面、WebView、浏览器或授权窗口。字体不随仓库分发；换字体后不能视为同一组样本。
- 三套模型依次运行，每套使用新进程。CPUExecutionProvider，intra-op 4 线程、inter-op 1 线程，检测长边上限 960，识别 batch=1，关闭方向分类。RapidOCR 初始化仍加载分类模型，因此 Python 内存包含它。
- 每套先识别浅色图预热，再对每个用例识别 5 次并取中位数。耗时包括图片解码、前后处理和识别；5 次文字均一致。未测 P95，未控制整机其他进程和温度。
- “首次识别合计”是模块导入、引擎初始化和首次调用之和，不含 Python 进程启动；此前已准备模型，操作系统文件缓存未清空或控制，不代表整机冷启动，也不能据此公平比较三者冷启动。
- 基准由 macOS sandbox-exec 禁网，Python socket 另拒绝连接。探针连接本机 127.0.0.1:9 返回 EPERM。模型准备阶段允许联网，识别阶段不联网；不代表已提供插件安全沙箱。
- 错误数为去除所有空白后的 Levenshtein 编辑距离，保留大小写、标点和全半角差异；**不衡量空格、代码缩进和换行恢复**。双栏要求先读完左栏，再读右栏。
- 单字体、少量合成样本用于发现问题，不能推算真实截图的通用准确率。手写、繁体、照片、复杂版面和大图上限尚未覆盖。

## 初始化、内存与分发体积

| 项目 | v5 mobile | v6 small | v6 tiny |
| --- | ---: | ---: | ---: |
| 导入 / 初始化 / 首次识别合计（ms） | 1088.79 | 318.93 | 256.82 |
| 进程峰值 RSS（MiB） | 659.36 | 645.12 | 483.97 |
| 末次识别后 RSS（MiB） | 548.36 | 414.09 | 438.34 |
| 检测 + 识别模型（MiB） | 20.46 | 29.72 | 6.03 |
| 模型 + 原生 ORT 库下限（MiB） | 54.10 | 63.36 | 39.67 |

原生 ORT 动态库实测 33.64 MiB，取自本机 wheel，已用 otool 查看动态依赖；没有构建独立原生 OCR 程序。表中的“下限”只累加检测模型、识别模型及该库，不含插件后端、预处理、几何裁切、DB 后处理、SDK、UI、许可文件和额外依赖，未测最终 ZIP。可选方向分类权重另约 0.56 MiB。

当前下载包和解压内容分别限 64 MiB。v6 small 配标准库只余不足 1 MiB，不能认定完整插件能装下；需要裁剪运行库或调整模型/分发设计。v5 mobile 和 tiny 空间更多，但同样未通过原生包验证。ZIP 压缩不能解决解压体积超限。

Python 的 rapidocr、onnxruntime、cv2、numpy 四个目录合计约 251.1 MiB，还未计解释器及其他依赖，不能当成精简原生包体积。

早期 batch=6 探测观察到约 840–884 MiB 峰值；batch=1 有改善但仍偏高。RSS 含解释器、OpenCV、ORT 和中间张量，不能直接推断 Go/C++ 成品内存。后续需验证原生峰值、多图及空闲回收；可评估按需加载或短生命周期 OCR 工作进程，同时保证取消、退出和后代进程回收。

## 复现

仓库根目录执行。示例路径适用于 macOS，其他系统自行指定中英文字体与输出目录。模型及图片不提交到仓库。

```sh
uv run --python 3.12 --locked --script scripts/ocr-validation.py prepare --profile v6-small --rec-batch 1 --out /tmp/sinan-ocr-repro/v6-small --font '/System/Library/Fonts/Hiragino Sans GB.ttc'
uv run --python 3.12 --locked --script scripts/ocr-validation.py benchmark --profile v6-small --rec-batch 1 --out /tmp/sinan-ocr-repro/v6-small
```

第二条命令在 Python 层禁网。复现本轮系统级禁网时，先在在线阶段准备好 Python 环境及模型，再使用以下命令；将 `<venv-python>` 替换为已准备环境的解释器路径。

```sh
/usr/bin/sandbox-exec -p '(version 1)(allow default)(deny network*)' <venv-python> scripts/ocr-validation.py benchmark --profile v6-small --rec-batch 1 --out /tmp/sinan-ocr-repro/v6-small
```

另两组改用 `v5-mobile`、`v6-tiny`，并使用各自输出子目录。输出包括 corpus、图片、预览、模型和 JSON。本次临时目录为 `/tmp/sinan-ocr-validation-20261116/`，不作为长期存档。提交的结果 JSON 保留文字、计时和模型摘要，省略坐标/置信度并将临时模型路径规范化。

## 下一阶段门槛

1. 构建原生 OCR 最小程序，以同一批图片核对预处理、DB 后处理、裁切、CTC 字典和输出，避免移植退化。
2. 验证完整插件解压后小于 64 MiB，核对具体模型与运行库许可；六个 OS/架构目标分别检查产物、依赖和模型加载。
3. 测试多图、大图、取消、超时和内存回收，再接入插件异步任务及界面。
4. 补充多字体及公开真实截图，确定默认模型。截图选区、剪贴板链路、焦点、DPI、Wayland Portal、系统授权和实机 UI 均未在本轮验证。
