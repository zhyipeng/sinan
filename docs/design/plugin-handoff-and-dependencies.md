# 跨插件页面交接与依赖检查设计

状态：用户已确认并实现，2026-11-17。本文保留设计背景；最终实现与限制以 [ADR 0080](../adr/0080-plugin-handoff-and-dependencies.md) 为准。

用户已选择：截图后处理中的 OCR 操作跳转到 OCR 插件继续处理。本轮先明确引擎、协议和依赖机制，再确认实施。

## 1. 交互与首版范围

截图后处理追加“OCR 识别”按钮。点击时导出当前编辑结果，包含已完成的裁剪和标注；宿主将图片交给 OCR 插件，在原所属窗口打开识别页面并自动识别，结果查看、编辑与复制由 OCR 页面提供。

OCR 是截图插件的可选依赖。缺少、禁用或版本不兼容时，截图、标注、导入、复制和保存照常可用；点击 OCR 时展示具体原因及“前往插件中心”入口。插件中心负责安装、更新与启用操作，沿用其既有用户操作流程。

首版形成通用的“公开页面入口 + 带类型数据交接”。后台服务的请求/返回型调用可在后续单独设计；当前 OCR 流程结束于目标页面，宿主无需转发识别结果到截图页面。

## 2. 现有能力与缺口

| 部分 | 当前源码状态 | 本次设计补充 |
| --- | --- | --- |
| 页面命令调用 | command.execute/executeImage 仅允许当前视图声明的同插件命令 | 按依赖和公开入口交接到目标页面 |
| OCR | start/poll/cancel 后台任务；页面收到 launch.image 后自动识别 | 显式声明可供其他插件打开的图片入口 |
| 图片会话 | 宿主持有 PNG，目标页面使用独立 sinan-plugin URL | 受限上传当前编辑结果，创建目标独立快照 |
| 页面切换 | 宿主已有 OpenUICommandWithPaste 和 PrepareEmbedded | 增加调用方校验、依赖校验及交接事务 |
| 插件依赖 | 当前 manifest 无依赖或跨插件公开入口声明 | 增加依赖、目标入口与视图授权声明 |

当前 OCR 0.2.0 已能接收宿主启动图片，但没有公开跨插件入口声明。因此接口接受图片与允许被其他插件调用需要分别验证。

## 3. 拟议 manifest 契约

下列字段都是拟议字段，确认后才同步协议、Schema、Go 校验器、TS 类型、SDK 和包校验。API 1 / UI Bridge 2 的增量通过新的 host capability 识别。

截图插件增加可选依赖，并仅授权编辑视图使用该依赖：

```json
{
  "dependencies": [
    {
      "id": "ocr",
      "pluginId": "tools.ocr",
      "minVersion": "0.3.0",
      "optional": true,
      "entries": [{"id": "recognize-image", "version": "1"}]
    }
  ],
  "contributes": {
    "uiViews": [{"id": "editor", "dependencies": ["ocr"]}]
  }
}
```

OCR 插件显式公开页面入口：

```json
{
  "contributes": {
    "entryPoints": [
      {
        "id": "recognize-image",
        "version": "1",
        "commandId": "open",
        "input": "image"
      }
    ]
  }
}
```

以上片段只展示新增字段；现有 commands、uiViews 和 permissions 继续保留。0.3.0 是建议的下一版 OCR 版本，尚未实现或发布，不代表登记仓库已有该版本。

- dependency.id 是消费方包内别名；宿主将别名解析到固定 pluginId，页面不接受任意目标插件 ID。
- 依赖绑定目标插件最低版本与入口协议版本，二者独立校验。首版使用现有三段数字版本规则，暂不引入完整 npm 版本范围语法。
- entryPoints 只能关联真实存在且带 uiView 的普通命令。searchOnly 后台命令、可信内置组件、任意 URL 或任意后台方法都不能作为此类入口。
- uiView.dependencies 是该视图的精确授权列表，仅声明 dependencies 不等于所有视图都能交接；既有 permissions 的数量上限保持不变。
- 校验别名、目标重复、入口存在性、版本格式、未知字段和硬依赖环。仅可选依赖形成的图不触发递归自动激活。

## 4. 引擎接口

拟新增 host capability：`ui.plugin-handoff.v1`。SDK 形态：

```js
const dependencies = await readDependencies();
const imageHandle = await stageDependencyImage(
  'ocr', 'recognize-image', await editor.exportPNG()
);
await openDependency('ocr', 'recognize-image', {imageHandle});
```

接口都以宿主持有的当前 Session 确认调用者身份。readDependencies 仅返回本视图已声明的依赖；上传和交接都再次校验别名、入口和版本。imageHandle 只代表一份内存 PNG，绑定源会话、目标依赖和目标入口，单次消费，过期或撤销后失效。

目标页面收到新的 launch.image URL；源图片 URL、上传句柄、源会话调用权限和文件路径均不传递给目标。OCR 页面继续采用 readLaunch + executeImage 的已有工作流。

依赖预检包括：已安装、启用、所需版本、目标公开入口/版本、包指纹及当前平台原生入口。预检通过表示具备启动条件；动态库、模型和初始化失败仍须在实际打开时明确报告，不将静态检查描述为运行可用保证。

## 5. 图片传输与预算

识别当前编辑结果需要把 Canvas 导出内容交给宿主。现有每 36 KiB 走一次普通命令的做法受每分钟 120 次调用限制，较大图片与此前截图读取叠加后会耗尽预算，因此交接设计包含专门的受限图片暂存通道。

- 每张 PNG 最多 4 MiB、1600 万像素，与现有目标 launch.image/executeImage 边界一致。截图编辑器自身 8 MiB/3200 万像素的边界不变；超出 OCR 交接限制时提示先裁剪，不自动改变分辨率。
- 数据帧保持每块最多 36 KiB、单请求最多 64 KiB；严格连续偏移，除最后一块外固定块长，一张图最多 114 个数据帧。源图上传结束后，宿主完整解码校验，不仅验证 PNG 文件头。
- 普通控制调用继续受既有速率、并发及消息预算约束。仅已登记且仍有效的图片数据帧使用独立预算：每会话一份在途上传，每分钟最多两份/8 MiB；不得凭自称上传方法绕过其他请求校验。三端原生桥均需同步分离计数，不能只调整页面 JS。
- 上传句柄绑定一个目标；空闲 15 秒取消，上传总时间最多 60 秒；校验后的待交接句柄保留 30 秒，消费或撤销立即释放。完整解码和资源持有始终计入宿主内存限额。
- 交接控制调用建议 10 秒预算，页面桥等待 12 秒；图片上传、页面准备与 OCR 识别各自有独立生命周期。现有 OCR 的 30 秒识别预算继续由 OCR 插件管理。

暂存属于通用图像输入机制，业务识别逻辑仍留在 OCR 插件；图像不经过系统剪贴板，不通过本地路径共享。

## 6. 交接事务与撤销

1. 点击 OCR 后检查依赖状态；保留当前截图编辑页面。
2. 导出当前图片并暂存到宿主；失败仍停留在原页面。
3. 开始交接时锁定源会话、所属窗口打开序号、目标实例及包指纹；重新校验全部条件。
4. 准备目标隔离视图和独立图片快照。目标页面的启动图片和业务启动要在交接提交后交付；ready 握手不能提前启动 OCR，需为“准备/激活”增加明确的宿主门控。
5. 目标准备成功后，原子替换窗口当前视图并激活目标，最后撤销源页面与暂存句柄。目标任务随后由目标会话管理；源会话的撤销不能误取消已经提交的目标。
6. 提交前发生取消、禁用、卸载、升级、包变化或页面准备失败，销毁待提交目标并保持源页面。提交后发生目标识别错误，则在 OCR 页面按其既有方式报告。

重复点击由源窗口的交接任务锁及单次句柄去重。成功不依赖源页面收到返回值：切换后源页面会被撤销，不能因此重复打开目标。只有一个窗口角色迁移，主窗口和拆出窗口都使用同一策略，不唤起无关窗口。

首版导航为单向替换。源编辑器及撤销历史在交接成功后释放；如需“一键返回并恢复标注历史”，应另设导航历史/编辑状态恢复能力，不在本次实现范围中默认承诺。

## 7. 依赖状态与管理

| 状态 | OCR 操作反馈 |
| --- | --- |
| available | 可交接；点击时再次校验 |
| missing | 提示安装 OCR，提供前往插件中心入口 |
| disabled | 提示启用 OCR |
| incompatible | 提示所需最低插件版本或入口协议版本 |
| changed / invalid | 提示重载或修复插件 |
| unsupported | 当前平台或宿主隔离承载缺少所需能力 |
| starting / busy | 防止重复交接，保留当前图片 |
| failed | 展示目标初始化或打开失败，可重试 |

插件安装、启动和卸载都需感知依赖图：允许安装缺少依赖的包并显示待补齐状态；硬依赖未满足时阻止消费方激活，optional 只影响对应入口。依赖安装、启用、禁用、更新、重载或卸载后重新计算；硬依赖变为不可用时阻止新调用并撤销相关在途操作。

插件中心展示依赖及被依赖关系、缺失原因和修复入口；卸载前展示依赖影响，沿用既有操作确认策略。首版所有安装/更新由用户从插件中心发起，依赖检查本身只读，不隐式联网或改变插件启用状态。

状态查询不会启动 OCR，也不会读取剪贴板。页面展示可缓存状态，但真正交接始终重新校验，不能依赖早先的查询结果。

## 8. 三仓库联动与实施顺序

1. **sinan**：先补 manifest/Schema/协议/SDK 和依赖图校验，再补会话绑定的依赖查询、图片暂存、页面交接事务、激活门控及插件中心状态 UI。确认后以 ADR 记录实际决策。
2. **sinan-official-plugins**：截图追加 OCR 入口和依赖声明；OCR 新版本公开图片入口并适配目标激活时机；更新 SDK 可追溯快照、跨平台构建、包校验和说明。
3. **sinan-plugin-registry**：新 OCR 与截图包真正发布后，再登记真实资产、依赖该能力的最低宿主版本。若商店需要展示依赖字段，先扩展发布 Schema/校验器再登记；设计阶段不改现有发布记录。

## 9. 验证与未决边界

无界面测试覆盖：依赖缺失/禁用/版本不兼容、未声明别名/入口、目标不公开、调用者伪造、句柄重放/串用/超时、图片损坏和配额、上传中退出、目标在检查后升级/卸载、准备失败保留源页、提交时源会话撤销与目标激活竞态、硬依赖图与环、源页成功退出不会取消目标。

平台代码需同步评估 macOS WKWebView、Windows WebView2、Linux WebKitGTK 的桥计数、资源、视图替换、激活时机及失焦。三端源码和交叉构建不代表原生运行或 UI 验收；日常验证只做无界面测试、静态检查和构建。真实桌面、WebView 与 OCR 跳转交互验收仍需用户明确要求。独立进程不是安全沙箱，原生插件保有当前用户权限。

用户已确认识别当前编辑结果，成功后切换到 OCR 并释放源编辑历史；本方案已进入实现，实际接口与验证边界见 ADR 0080。
